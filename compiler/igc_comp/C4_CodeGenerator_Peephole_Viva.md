# Viva Preparation — C4 Code Generator, Grammar, and Peephole Optimizer

This document explains the three uploaded files:

1. `C4.g4` — ANTLR4 grammar for the C4 language.
2. `CodeGenarator(1).cpp` — generates 32-bit x86/FASM-style assembly from the ANTLR parse tree.
3. `PeepholeOptimizer.cpp` — reads generated assembly and repeatedly applies local optimization patterns.

The explanations below follow the actual uploaded source code and its terminology.

---

# 1. Overall Project Flow

The project can be understood as a compiler pipeline:

```text
C4 source program
       |
       v
     C4.g4
       |
       | lexer + parser generated by ANTLR
       v
   Parse Tree
       |
       v
CodeGenarator visitor
       |
       v
Generated x86 assembly
       |
       v
PeepholeOptimizer
       |
       v
Optimized assembly
```

The important idea is that `C4.g4` defines what source programs look like, `CodeGenarator` walks the parse tree and emits assembly, and `PeepholeOptimizer` performs local assembly-level transformations.

---

# 2. `C4.g4` — Grammar

## 2.1 What is ANTLR grammar?

`C4.g4` is an ANTLR4 grammar.

It contains:

- **Parser rules** — describe the syntax/structure of programs.
- **Lexer rules** — describe keywords, operators, identifiers, constants, whitespace, and comments.

The grammar starts from:

```antlr
start : program ;
```

So `start` is the root parser rule.

---

# 3. Parser Rules in `C4.g4`

## 3.1 `start`

```antlr
start : program ;
```

This says a complete input is a `program`.

The parse-tree traversal begins from this structure.

---

## 3.2 `program`

```antlr
program
    : program unit
    | unit
    ;
```

A program consists of one or more `unit`s.

A `unit` can be:

- variable declaration
- function declaration
- function definition

This recursive structure allows multiple top-level declarations/definitions.

Example:

```c
int x;
int add(int a, int b) {
    return a + b;
}
```

contains multiple units.

---

## 3.3 `unit`

```antlr
unit
    : var_declaration
    | func_declaration
    | func_definition
    ;
```

This is the main top-level choice.

---

# 4. Function Syntax

## 4.1 Function declaration

```antlr
func_declaration
    : type_specifier ID LPAREN parameter_list RPAREN SEMICOLON
    | type_specifier ID LPAREN RPAREN SEMICOLON
    ;
```

It supports functions with parameters and functions without parameters.

Example:

```c
int add(int a, int b);
```

or:

```c
int foo();
```

The return type is represented by `type_specifier`.

The function name is an `ID`.

---

## 4.2 Function definition

```antlr
func_definition
    : type_specifier ID LPAREN parameter_list RPAREN compound_statement
    | type_specifier ID LPAREN RPAREN compound_statement
    ;
```

A definition contains the actual function body.

Example:

```c
int add(int a, int b)
{
    return a + b;
}
```

The body is represented by `compound_statement`.

---

## 4.3 `parameter_list`

```antlr
parameter_list
    : parameter_list COMMA type_specifier ID
    | parameter_list COMMA type_specifier
    | type_specifier ID
    | type_specifier
    ;
```

It supports:

```c
int a, int b
```

and also a type without an identifier according to the grammar:

```c
int, int
```

The code generator later counts parameters and collects named parameters.

---

# 5. Compound Statements

```antlr
compound_statement
    : LCURL statements RCURL
    | LCURL RCURL
    ;
```

A compound statement is a block:

```c
{
    statement1;
    statement2;
}
```

It can also be empty:

```c
{
}
```

The code generator creates a symbol-table scope for blocks in several statement contexts.

---

# 6. Variable Declarations

## 6.1 `var_declaration`

```antlr
var_declaration
    : type_specifier declaration_list SEMICOLON
    ;
```

Example:

```c
int x, y;
```

or:

```c
int a[10];
```

---

## 6.2 `type_specifier`

```antlr
type_specifier
    : INT
    | FLOAT
    | VOID
    ;
```

Supported types are:

- `int`
- `float`
- `void`

The code generator has special handling for `void` variable declarations: it simply returns without generating storage.

---

## 6.3 `declaration_list`

```antlr
declaration_list
    : declaration_list COMMA ID
    | declaration_list COMMA ID LTHIRD CONST_INT RTHIRD
    | ID
    | ID LTHIRD CONST_INT RTHIRD
    ;
```

This supports normal variables and arrays.

Examples:

```c
int x;
```

```c
int x, y, z;
```

```c
int a[10];
```

The array size must be a `CONST_INT` according to the grammar.

---

# 7. Statements

The grammar supports:

```antlr
statement
    : var_declaration
    | expression_statement
    | compound_statement
    | FOR ...
    | IF ...
    | WHILE ...
    | PRINTLN ...
    | RETURN ...
    ;
```

So the language includes:

- local declarations
- expressions
- blocks
- `for`
- `if`
- `if-else`
- `while`
- `println`
- `return`

---

# 8. `expression_statement`

```antlr
expression_statement
    : SEMICOLON
    | expression SEMICOLON
    ;
```

This represents:

```c
;
```

or:

```c
x = 10;
```

It is particularly important for the `for` statement because the initialization and condition are represented as expression statements.

---

# 9. Variables and Arrays

```antlr
variable
    : ID
    | ID LTHIRD expression RTHIRD
    ;
```

This means:

```c
x
```

and:

```c
a[i]
```

are both variables.

The index is a complete expression, so something such as:

```c
a[i + 1]
```

can be represented.

---

# 10. Expression Hierarchy

The grammar separates expressions into levels.

```text
expression
    |
logic_expression
    |
rel_expression
    |
simple_expression
    |
term
    |
unary_expression
    |
factor
```

This hierarchy gives the language different precedence levels.

The approximate structure is:

```text
factor
   ↓
unary expression
   ↓
multiplication/division/modulo
   ↓
addition/subtraction
   ↓
relational operators
   ↓
logical operators
   ↓
assignment
```

This hierarchy is directly reflected in the visitor functions of `CodeGenarator`.

---

# 11. `expression`

```antlr
expression
    : logic_expression
    | variable ASSIGNOP logic_expression
    ;
```

An expression can either be a normal logical expression:

```c
a + b
```

or an assignment:

```c
a = b + 1
```

The code generator checks `ctx->ASSIGNOP()` to determine whether it is generating an assignment.

---

# 12. Logical Expressions

```antlr
logic_expression
    : rel_expression
    | rel_expression LOGICOP rel_expression
    ;
```

Supported logical operators are:

```antlr
LOGICOP : '&&' | '||' ;
```

So:

```c
a < b && c < d
```

is possible.

The code generator implements short-circuit-style control flow using labels and jumps.

---

# 13. Relational Expressions

```antlr
rel_expression
    : simple_expression
    | simple_expression RELOP simple_expression
    ;
```

Supported relational operators:

```text
==
!=
<=
>=
<
>
```

The generated result is normalized to:

```text
0 = false
1 = true
```

---

# 14. Addition and Subtraction

```antlr
simple_expression
    : term
    | simple_expression ADDOP term
    ;
```

`ADDOP` is:

```antlr
ADDOP : '+' | '-' ;
```

So:

```c
a + b
a - b
```

are handled here.

---

# 15. Multiplication, Division, Modulo

```antlr
term
    : unary_expression
    | term MULOP unary_expression
    ;
```

`MULOP` contains:

```text
*
/
%
```

The code generator uses `MUL` and `DIV`.

For modulo, it takes the remainder from `EDX`.

---

# 16. Unary Expressions

```antlr
unary_expression
    : ADDOP unary_expression
    | NOT unary_expression
    | factor
    ;
```

This supports:

```c
-x
+x
!x
```

The generated code handles unary minus using:

```asm
NEG EAX
```

Logical NOT is implemented using `TEST` and conditional jumps.

---

# 17. Factors

```antlr
factor
    : variable
    | ID LPAREN argument_list RPAREN
    | LPAREN expression RPAREN
    | CONST_INT
    | CONST_FLOAT
    | variable INCOP
    | variable DECOP
    ;
```

Factors include:

- variables
- function calls
- parenthesized expressions
- integer constants
- floating constants
- postfix increment
- postfix decrement

---

# 18. Function Arguments

```antlr
argument_list
    : arguments
    |
    ;
```

The empty alternative means a function may have no arguments.

Arguments are:

```antlr
arguments
    : arguments COMMA logic_expression
    | logic_expression
    ;
```

The code generator collects arguments and pushes them in reverse order.

---

# 19. Lexer Rules

Important keywords are:

```text
if
else
for
while
int
float
void
return
println
```

Operators include:

```text
=
&& ||
== != <= >= < >
+ -
* / %
++
--
!
```

Identifiers use:

```antlr
ID : [a-zA-Z_][a-zA-Z0-9_]* ;
```

Integer constants:

```antlr
CONST_INT : [0-9]+ ;
```

Floating constants support decimal/exponent forms.

Whitespace and comments are skipped:

```antlr
WS            : [ \t\r\n]+ -> skip ;
COMMENT       : '//' ~[\r\n]* -> skip ;
BLOCK_COMMENT : '/*' .*? '*/' -> skip ;
```

Therefore comments do not appear as normal parser nodes.

# 20. `CodeGenarator(1).cpp` — Main Purpose

The `CodeGenarator` class is an ANTLR parse-tree visitor.

Its job is to:

1. Visit grammar nodes.
2. Look up symbols in the symbol table.
3. Determine storage locations.
4. Generate assembly instructions.
5. Generate labels for control flow.
6. Generate function prologue/epilogue.
7. Generate runtime output code for `println`.

The visitor methods correspond closely to grammar rules.

For example:

```text
visitProgram()
visitFunc_definition()
visitVar_declaration()
visitStatement()
visitExpression()
visitTerm()
visitFactor()
```

---

# 21. Constructor

```cpp
CodeGenarator::CodeGenarator(const string& outputFileName)
    : labelCount(0), currentLine(1), paramCount(0) {
    asmFile.open(outputFileName);
    if (!asmFile.is_open()) {
        cerr << "Error: Cannot open output file " << outputFileName << endl;
    }
    out = &asmFile;
}
```

The constructor initializes:

- `labelCount = 0`
- `currentLine = 1`
- `paramCount = 0`

Then it opens the output assembly file.

`out` is a pointer to the output stream and initially points to `asmFile`.

The stream pointer is later temporarily redirected to an `ostringstream` when a function body is generated.

---

# 22. Destructor

```cpp
CodeGenarator::~CodeGenarator() {
    if (asmFile.is_open()) asmFile.close();
}
```

If the assembly file is still open, it closes it.

# 26. Operand Addressing — `getOperandAddr()`

```cpp
string CodeGenarator::getOperandAddr(SymbolInfo* sym)
```

This converts a symbol into its assembly memory address.

## Global variable

For a global variable named `x`:

```text
[x]
```

is returned.

## Local/parameter

For a symbol with a positive stack offset:

```text
[EBP+offset]
```

For a negative offset:

```text
[EBP-offset]
```

This is based on the function frame using `EBP`.

---

# 27. Array Address — `getArrayAddr()`

```cpp
string CodeGenarator::getArrayAddr(SymbolInfo* sym,
                                   const string& indexReg)
```

This creates an address for an array element.

For a global array:

```text
[array + indexReg]
```

For a local array:

```text
[EBP + indexReg - baseOffset]
```

In the actual visitor code, array indexing is also calculated directly rather than always calling this helper.

# 28. Relational Operator to Jump

```cpp
string CodeGenarator::relOpToJump(const string& op, bool negate)
```

This converts C-style relational operators into x86 conditional jumps.

Without negation:

| Operator | Jump |
|---|---|
| `==` | `JE` |
| `!=` | `JNE` |
| `<` | `JL` |
| `>` | `JG` |
| `<=` | `JLE` |
| `>=` | `JGE` |

With negation, the opposite jump is returned.

Example:

```text
==  -> JNE
<   -> JGE
>=  -> JL
```

If no known operator is found, the function returns `JMP`.

# 29. Assembly Header

`generateHeader()` emits:

```asm

```

This establishes an ELF executable format and identifies `main` as the entry point.

# 30. Data Segment

`generateDataSegment()` checks:

```cpp
if (!dataSegmentGlobals.empty())
```

If global variables exist, it generates:

```asm
segment readable writeable
```

Each global name is emitted as:

```asm
name dd 1 dup (0)
```

So global storage is allocated and initialized to zero.

---

# 31. Code Segment

`generateCodeSegmentStart()` emits:

```asm
segment readable executable
```

This starts the executable code section.

---

# 32. `OUTDEC` Runtime Procedure

`generateOutdecProcedure()` generates a complete assembly procedure called:

```asm
OUTDEC:
```

Its purpose is to print the integer stored in `EAX` as decimal followed by a newline.

The procedure saves:

```asm
PUSH EBX
PUSH ECX
PUSH EDX
PUSH ESI
```

This preserves registers it uses.

---

# 33. Negative Number Handling in `OUTDEC`

The code checks:

```asm
OR EAX, EAX
JGE OUTDEC_POSITIVE
```

If `EAX` is negative:

```asm
NEG EAX
```

Then it writes the `-` character using Linux `int 0x80`.

For the Linux 32-bit `write` system call, the code uses:

```asm
MOV EAX, 4
MOV EBX, 1
MOV ECX, ESP
MOV EDX, 1
INT 0x80
```

Here:

- `EAX = 4` → write syscall
- `EBX = 1` → stdout
- `ECX` → address of data
- `EDX = 1` → one byte

---

# 34. Decimal Digit Conversion

The positive number is converted using repeated division by 10:

```asm
MOV EBX, 10
...
DIV EBX
```

`DIV` produces:

```text
EAX = quotient
EDX = remainder
```

The remainder is converted into an ASCII digit:

```asm
ADD DL, 30h
```

The digit is pushed onto the stack.

Digits are pushed in reverse order, so later popping/printing produces the correct order.

---

# 35. Printing Digits

The procedure uses:

```asm
OUTDEC_PRINT_LOOP:
```

It repeatedly writes one digit using `int 0x80`.

After all digits are printed, it writes ASCII newline:

```asm
MOV byte [ESP], 10
```

Finally it restores registers:

```asm
POP ESI
POP EDX
POP ECX
POP EBX
RET
```

---

# 36. Function Prologue

```cpp
void CodeGenarator::generateFunctionPrologue(const string& funcName)
```

It emits:

```asm
funcName:
    PUSH EBP
    MOV EBP, ESP
```

This creates a standard stack frame.

After:

```asm
PUSH EBP
MOV EBP, ESP
```

the function can use `EBP` as a stable reference point for parameters and local variables.

---

# 37. Function Epilogue

```cpp
generateFunctionEpilogue(
    const string& funcName,
    int localSize,
    int paramSize)
```

It creates:

```text
funcName_exit:
```

If local storage exists, it releases it:

```asm
ADD ESP, localSize
```

Then:

```asm
POP EBP
```

For `main`, the code exits through Linux syscall:

```asm
MOV EBX, EAX
MOV EAX, 1
INT 0x80
```

For other functions with parameters:

```asm
RET paramSize
```

Otherwise:

```asm
RET
```

So `paramSize` is used to clean parameters from the stack for non-main functions.

antlrcpp::Any CodeGenarator::visitStart(

The visitor starts by visiting the `program` node.

# 40. `visitProgram()` — Important Two-Pass Structure

`visitProgram()` performs two major tasks.

First it recursively collects global variable declarations:

```cpp
collectUnits(...)
```

Then it emits:

```text
header
data segment
code segment
```

Then it recursively generates function definitions:

```cpp
generateFuncs(...)
```

Finally it emits `OUTDEC`.

The important reason for collecting globals first is that the data segment must be known before the code segment is emitted.

---

# 41. Why `visitProgram()` Uses Recursive Lambdas

The grammar is recursive:

```antlr
program
    : program unit
    | unit
```

Therefore the code walks through nested `program` nodes.

The lambdas:

```cpp
collectUnits
generateFuncs
```

recursively move toward the first program node and then process units.

This lets the implementation handle all top-level units.

---

# 42. `visitUnit()`

```cpp
if (ctx->var_declaration())
    visit(ctx->var_declaration());
else if (ctx->func_declaration())
    visit(ctx->func_declaration());
else if (ctx->func_definition())
    visit(ctx->func_definition());
```

It determines which kind of top-level unit was parsed and calls the corresponding visitor.

# 43. Function Declaration

`visitFunc_declaration()` obtains:

```cpp
string funcName = ctx->ID()->getText();
string returnType = ctx->type_specifier()->getText();
```

Then:

```cpp
symbolTable.insert(funcName, returnType);
```

So a function declaration records the function name and return type in the symbol table.

No assembly body is generated here.

---

# 44. Function Definition

`visitFunc_definition()` is one of the most important functions.

It:

1. Gets the function name and return type.
2. Stores the current function name.
3. Counts parameters.
4. Inserts the function into the symbol table.
5. Enters a new scope.
6. Assigns stack offsets to parameters.
7. Generates the body into a temporary buffer.
8. Determines local stack size.
9. Leaves the symbol scope.
10. Restores the real output stream.
11. Emits the function prologue.
12. Allocates local variables.
13. Copies the buffered body to the assembly output.
14. Emits the epilogue.

---

# 45. Parameter Counting

The code recursively traverses `parameter_list`.

Each parameter containing an `ID` increases the count.

Example:

```c
int f(int a, int b, int c)
```

gives:

```text
paramCount = 3
```

---

# 46. Parameter Stack Offsets

The code starts with:

```cpp
int paramOffset = 8;
```

Parameters are therefore initially associated with:

```text
[EBP+8]
[EBP+12]
[EBP+16]
...
```

This follows the stack-frame arrangement after the prologue:

```asm
PUSH EBP
MOV EBP, ESP
```

The code assigns each named parameter a 4-byte increment.

---

# 47. Parameter Symbol Information

For every named parameter:

```cpp
SymbolInfo* sym = new SymbolInfo(p.first, p.second);
```

Then:

```cpp
sym->setIdentityType("VAR");
sym->setIsGlobal(false);
sym->setStackOffset(paramOffset);
symbolTable.insert(sym);
```

So the symbol table knows:

- name
- type
- variable identity
- local/non-global status
- stack offset

---

# 48. Temporary Function Body Buffer

The code saves:

```cpp
ostream* savedOut = out;
```

and creates:

```cpp
ostringstream bodyBuffer;
out = &bodyBuffer;
```

The function body is generated into memory instead of immediately being written to the final assembly file.

After visiting the body, the code calculates local size.

Then:

```cpp
out = savedOut;
```

restores the original output stream.

This allows the prologue and local allocation to be emitted before the already-generated body.

---

# 49. Local Stack Size

After visiting the compound statement:

```cpp
ScopeTable* funcScope = symbolTable.getCurrentScope();
int localSize = funcScope->getCurrentStackOffset();
```

The current scope contains the information about local allocation.

Then the function scope is exited.

If `localSize > 0`:

```asm
SUB ESP, localSize
```

allocates space for local variables.

# 50. `visitCompound_statement()`

```cpp
if (ctx->statements()) {
    visit(ctx->statements());
}
```

It simply visits all statements in the block if the block is non-empty.

---

# 51. `visitVar_declaration()`

This function handles both global and local declarations.

First it gets the type:

```cpp
string type = ctx->type_specifier()->getText();
```

If the type is `void`:

```cpp
if (type == "void") return nullptr;
```

No variable storage is generated.

---

# 52. Collecting Declarations

The function recursively processes `declaration_list`.

For each declaration it stores:

```text
name
array size
```

For a normal variable:

```text
array size = 0
```

For an array:

```text
array size > 0
```

---

# 53. Detecting Global Variables

The code uses:

```cpp
bool isGlobal =
    (symbolTable.getCurrentScope()->getId() == 1);
```

If the current scope ID is 1, the declaration is treated as global.

Global names are added to:

```cpp
dataSegmentGlobals
```

---

# 54. Global Variable vs Global Array

For a global array:

```cpp
sym->setIdentityType("ARRAY");
sym->setArraySize(decl.second);
sym->setIsGlobal(true);
```

For a normal global variable:

```cpp
sym->setIdentityType("VAR");
sym->setIsGlobal(true);
```

Both have:

```cpp
setStackOffset(0)
```

because they are not stored in the local stack frame.

---

# 55. Local Variables

For local arrays:

```cpp
symbolTable.allocateLocalArray(...)
```

For local variables:

```cpp
symbolTable.allocateLocalVar(...)
```

The symbol table therefore controls the stack allocation information.

# 56. `visitStatements()`

```cpp
if (ctx->statements()) {
    visit(ctx->statements());
}

visit(ctx->statement());
```

Because the grammar is:

```antlr
statements
    : statement
    | statements statement
    ;
```

the function recursively visits previous statements and then the current statement.

# 57. `visitStatement()` — Control Flow

This is another major function.

It handles:

- declaration
- `for`
- expression statement
- block
- `if`
- `if-else`
- `while`
- `println`
- `return`

---

# 58. `for` Loop Generation

For:

```c
for (initialization; condition; update)
    body;
```

the code creates:

```text
for_start_X
for_end_X
for_body_X
```

Although `bodyLabel` is created, the actual generated flow does not emit the `bodyLabel`.

The generated structure is essentially:

```text
initialization

for_start:
    condition
    TEST EAX,EAX
    JE for_end

    body

    update
    JMP for_start

for_end:
```

---

# 59. `for` Loop Scope

The code enters a symbol-table scope before processing the `for` components:

```cpp
symbolTable.enterScope();
```

and exits it afterward:

```cpp
symbolTable.exitScope();
```

This gives the loop's generated declarations a scoped symbol-table context.

---

# 60. `if` Without `else`

For:

```c
if (condition)
    statement;
```

the code creates:

```text
if_end_X
```

Then:

```asm
TEST EAX, EAX
JE if_end_X
```

If the condition is zero, execution jumps over the body.

---

# 61. `if-else`

For:

```c
if (condition)
    statement1;
else
    statement2;
```

two labels are generated:

```text
if_else_X
if_end_X
```

The flow is:

```text
evaluate condition
TEST EAX,EAX
JE if_else

then body
JMP if_end

if_else:
else body

if_end:
```

---

# 62. `while`

For:

```c
while (condition)
    body;
```

the code creates:

```text
while_start_X
while_end_X
```

Flow:

```text
while_start:
    evaluate condition
    TEST EAX,EAX
    JE while_end

    body
    JMP while_start

while_end:
```

---

# 63. `println`

The grammar supports:

```c
println(x);
```

The code looks up the identifier:

```cpp
SymbolInfo* sym = symbolTable.lookUp(varName);
```

Then it saves the current `EAX`:

```asm
PUSH EAX
```

loads the variable value into `EAX`:

```asm
MOV EAX, address
```

calls:

```asm
CALL OUTDEC
```

and restores the previous `EAX`:

```asm
POP EAX
```

---

# 64. `return`

For:

```c
return expression;
```

the code:

1. Visits the expression.
2. Leaves the result in `EAX`.
3. Jumps to the current function's exit label.

Example:

```asm
JMP add_exit
```

This means all return paths can converge at one epilogue.

---

# 65. `visitExpression_statement()`

If an expression exists:

```cpp
visit(ctx->expression());
```

Otherwise it is simply an empty statement:

```c
;
```

---

# 66. `visitVariable()`

This function loads a variable value into `EAX`.

For:

```c
x
```

it looks up `x`.

For an array:

```c
a[i]
```

it evaluates the index.

---

# 67. Array Index Calculation

The code does:

```asm
MOV EBX, 4
MUL EBX
```

This converts an integer array index into a byte offset.

For 4-byte elements:

```text
byte offset = index * 4
```

So:

```c
a[3]
```

uses:

```text
3 * 4 = 12
```

as the byte offset.

---

# 68. Global Array Access

For a global array:

```asm
MOV EAX, [array + EAX]
```

The computed byte offset is added to the array base.

---

# 69. Local Array Access

For a local array, the code adjusts the index using its stack offset:

```asm
SUB EAX, baseOffset
NEG EAX
MOV EAX, [EBP + EAX]
```

This converts the calculated index into the corresponding frame address.

---

# 70. Assignment Generation

`visitExpression()` checks:

```cpp
if (ctx->ASSIGNOP())
```

If true, it is an assignment.

For example:

```c
x = expression;
```

the right side is evaluated first:

```cpp
visit(ctx->logic_expression());
```

The result is placed in `EAX`.

Then it is stored into the variable.

---

# 71. Normal Variable Assignment

For a global:

```asm
MOV [x], EAX
```

For a local variable:

```asm
MOV [EBP-offset], EAX
```

using `getOperandAddr()`.

---

# 72. Array Assignment

For:

```c
a[i] = value;
```

the code first evaluates the index.

Then:

```asm
MOV EBX, 4
MUL EBX
PUSH EAX
```

The index byte offset is saved.

Then the right-hand side is evaluated.

Afterward:

```asm
POP EBX
```

restores the array byte offset.

The result is stored into the selected array element.

---

# 73. Logical `&&`

For:

```c
a && b
```

the first operand is evaluated.

```asm
TEST EAX,EAX
JE falseLabel
```

If it is false, the second operand does not need to determine a true result.

The code eventually produces:

```text
EAX = 0
```

or:

```text
EAX = 1
```

This implements short-circuit-style AND behavior.

---

# 74. Logical `||`

For:

```c
a || b
```

the first operand is evaluated.

```asm
TEST EAX,EAX
JNE falseLabel
```

The label name is `falseLabel`, although in the `||` branch it is used as the successful true-result path.

At that label:

```asm
MOV EAX, 1
```

So the same label variable is used with different semantic roles depending on the operator.

---

# 75. Relational Expression Generation

For:

```c
a < b
```

the code:

1. Evaluates the first expression.
2. Pushes its result.
3. Evaluates the second expression.
4. Pops the first result into `EBX`.
5. Compares them.
6. Jumps if the relation is true.
7. Produces `0` otherwise.
8. Produces `1` if true.

Core instructions:

```asm
CMP EBX, EAX
JL relop_true_X
MOV EAX, 0
JMP relop_end_X

relop_true_X:
MOV EAX, 1

relop_end_X:
```

---

# 76. Why `CMP EBX, EAX`?

The first operand is saved in `EBX`:

```asm
PUSH EAX
```

Then the second operand becomes `EAX`.

After:

```asm
POP EBX
```

we have:

```text
EBX = left operand
EAX = right operand
```

Then:

```asm
CMP EBX, EAX
```

sets the flags based on the subtraction-like comparison.

---

# 77. Addition/Subtraction

For a binary expression, the left side is evaluated and pushed.

Then the right side is evaluated.

After popping the left side:

```asm
POP EBX
```

For addition:

```asm
ADD EAX, EBX
```

Since addition is commutative, this gives the same sum.

For subtraction:

```asm
XCHG EAX, EBX
SUB EAX, EBX
```

After `XCHG`:

```text
EAX = left
EBX = right
```

so:

```asm
SUB EAX, EBX
```

correctly calculates:

```text
left - right
```

---

# 78. Multiplication

For:

```c
a * b
```

the left side is saved in `EBX`, while the right side is in `EAX`.

The code emits:

```asm
MUL EBX
```

The unsigned multiplication uses `EAX` as an implicit operand and produces the result across `EDX:EAX`.

---

# 79. Division

For division, the code swaps the operands:

```asm
XCHG EAX, EBX
XOR EDX, EDX
DIV EBX
```

The purpose of:

```asm
XOR EDX, EDX
```

is to clear the high half used by unsigned `DIV`.

After division:

```text
EAX = quotient
EDX = remainder
```

---

# 80. Modulo

For:

```c
a % b
```

the code also performs `DIV`.

Then:

```asm
MOV EAX, EDX
```

moves the remainder into `EAX`.

So the final expression value is the remainder.

---

# 81. Unary Minus

For:

```c
-x
```

the code evaluates `x` into `EAX` and then:

```asm
NEG EAX
```

which changes:

```text
x -> -x
```

---

# 82. Logical NOT

For:

```c
!x
```

the code does:

```asm
TEST EAX,EAX
JNE not_true_X
MOV EAX,1
JMP not_end_X

not_true_X:
MOV EAX,0

not_end_X:
```

Therefore:

```text
x == 0  -> 1
x != 0  -> 0
```

---

# 83. Variables and Postfix `++` / `--`

For:

```c
x++
```

the code first loads the original value:

```asm
MOV EAX, value
PUSH EAX
```

Then it increments the actual memory location:

```asm
INC dword [...]
```

Finally:

```asm
POP EAX
```

restores the original value as the expression result.

This is important because postfix increment returns the old value.

Similarly, `x--` uses `DEC`.

---

# 84. Array Postfix Increment/Decrement

For:

```c
a[i]++
```

the code:

1. Evaluates `i`.
2. Multiplies by 4.
3. Calculates the element address.
4. Loads the old value.
5. Pushes the old value.
6. Increments/decrements the actual element.
7. Pops the old value into `EAX`.

Thus the expression result remains the old value.

---

# 85. Function Calls

For:

```c
foo(a, b, c)
```

the code collects argument expressions.

Then it loops from the last argument to the first:

```cpp
for (int i = (int)argExprs.size() - 1; i >= 0; i--)
```

Each argument is evaluated and pushed:

```asm
PUSH EAX
```

Then:

```asm
CALL foo
```

is emitted.

This is a right-to-left argument push order.

---

# 86. Function Return Value

The code generator assumes expression results are carried in:

```text
EAX
```

Therefore a function call leaves its return value in `EAX`, which can immediately be used by the surrounding expression.

---

# 87. Parenthesized Expression

For:

```c
(a + b)
```

the code simply visits:

```cpp
ctx->expression()
```

The parentheses themselves do not require assembly instructions.

Their effect has already been represented by the parse tree.

---

# 88. Integer Constants

For:

```c
123
```

the code emits:

```asm
MOV EAX, 123
```

Therefore constants become immediate values in `EAX`.

---

# 89. Floating Constants

The code currently handles floating constants as:

```asm
MOV EAX, 0  ; float constant ignored
```

This is an important limitation to remember for viva.

Although `C4.g4` recognizes `float` and `CONST_FLOAT`, the shown code generator does not implement real floating-point code generation.

---

# 90. Empty Visitor Functions

The following visitor methods return `nullptr` without directly generating code:

```cpp
visitParameter_list()
visitType_specifier()
visitDeclaration_list()
visitArgument_list()
visitArguments()
```

This is because their work is handled by their parent visitor methods or because they are structural grammar nodes.

For example, `visitFunc_definition()` explicitly collects parameters instead of relying on `visitParameter_list()`.

# 91. `PeepholeOptimizer.cpp` — Main Purpose

The peephole optimizer works on generated assembly as text.

It:

1. Loads assembly lines into a vector.
2. Normalizes instructions.
3. Detects small local patterns.
4. Removes or replaces redundant instructions.
5. Repeats until no more changes are possible.
6. Writes the optimized assembly.

A peephole optimizer examines a small window of nearby instructions rather than rebuilding the entire program.

---

# 92. Constructor

```cpp
PeepholeOptimizer::PeepholeOptimizer()
    : optimizationsCount(0) {}
```

The optimization counter starts at zero.

The destructor is empty.

---

# 93. `trim()`

```cpp
string PeepholeOptimizer::trim(const string& str)
```

This removes leading and trailing:

```text
space
tab
carriage return
newline
```

If the entire string is whitespace, it returns an empty string.

This is useful because assembly formatting can contain different amounts of whitespace.

---

# 94. `isLabel()`

```cpp
bool PeepholeOptimizer::isLabel(const string& line)
```

It trims the line and checks whether the last character is:

```text
:
```

Example:

```asm
loop_start:
```

is recognized as a label.

---

# 95. `isEmptyOrComment()`

This returns true if the line is:

- empty
- starts with `;`

It recognizes assembly comments.

---

# 96. `normalizeInstruction()`

This is very important.

It:

1. Trims whitespace.
2. Removes everything after `;`.
3. Compresses multiple spaces/tabs into one space.
4. Converts the instruction to uppercase.
5. Trims the final result.

For example, something like:

```asm
    mov   eax, 5    ; load value
```

becomes approximately:

```text
MOV EAX, 5
```

This makes pattern matching much easier.

---

# 97. Redundant `MOV`

`isRedundantMOV()` detects a two-instruction swap:

```asm
MOV A, B
MOV B, A
```

The second move can be redundant under the assumptions made by this optimizer.

The code extracts:

```text
dest1
src1
dest2
src2
```

and checks:

```cpp
dest1 == src2 && src1 == dest2
```

If true, the second instruction is removed.

---

# 98. Redundant `PUSH` / `POP`

`isRedundantPushPop()` detects:

```asm
PUSH EAX
POP EAX
```

Since the same value is immediately pushed and restored to the same register, the pair has no useful effect under the optimizer's local assumptions.

Both instructions are removed.

---

# 99. Redundant Arithmetic

`isRedundantArithmetic()` detects operations that do not change the mathematical value.

Examples:

```asm
ADD EAX, 0
SUB EAX, 0
MUL EAX, 1
```

It also recognizes some `AND` identities:

```asm
AND ..., -1
AND ..., 0FFFFFFFF
AND ..., 0FF
```

according to the exact string tests in the uploaded source.

Such instructions are removed.

---

# 100. Consecutive Labels

`isConsecutiveLabels()` returns true when both lines are labels.

Example:

```asm
label1:
label2:
```

The optimizer then checks whether later labels are referenced before removing an unreferenced label.

---

# 101. Jump to the Immediately Next Label

`isRedundantJmpToNextLabel()` detects:

```asm
JMP label1
label1:
```

The jump is unnecessary because execution reaches `label1` naturally.

The `JMP` is removed.

---

# 102. Redundant Load After Store

`isRedundantLoadAfterStore()` looks for a pattern such as:

```asm
MOV [memory], register
MOV register, [memory]
```

The second instruction reloads exactly what was just stored.

The optimizer removes the second `MOV`.

It specifically checks that the first destination and second source look like memory operands.

---

# 103. Constant Store Simplification

`isConstantStoreSimplifiable()` recognizes a pattern where a constant is loaded into a register and then the register is stored into memory.

Conceptually:

```asm
MOV EAX, 5
MOV [x], EAX
```

can become:

```asm
MOV dword [x], 5
```

The optimizer therefore removes the first `MOV` and modifies the second one.

This reduces two instructions to one.

---

# 104. `foldPushOverwritePop()`

This is a more specialized optimization.

It looks for four instructions:

```text
MOV register, source
PUSH register
MOV register, immediate
POP another_register
```

The function checks whether the original value of the first register is overwritten before being restored in a way that makes the original save unnecessary.

If the conditions are satisfied, it produces:

```asm
MOV another_register, source
```

This is a local data-flow simplification.

The code explicitly rejects cases where the source contains `ESP` or the destination register.

---

# 105. `findMatchingPop()`

This searches forward for a matching:

```asm
POP register
```

after:

```asm
PUSH register
```

The maximum search distance is:

```cpp
const size_t maxLookahead = 6;
```

So the optimizer does not search indefinitely.

It stops if:

- another `PUSH` of the same register is encountered
- a matching `POP` is found
- a label is encountered
- a removed line is encountered

---

# 106. `isDeadRegisterOverwrite()`

This checks whether a register is overwritten after its matching `POP`.

It expects a `MOV`.

Example conceptual pattern:

```asm
POP EAX
MOV EAX, EBX
```

If the new `MOV` does not use `EAX` as its source, the old value restored by `POP EAX` is immediately destroyed.

Therefore the earlier `PUSH EAX` and `POP EAX` may be unnecessary.

---

# 107. Label Utility Functions

`isEmptyLine()` checks whether a line contains only whitespace.

`getLabelName()` removes the trailing `:` from a label.

Example:

```text
loop_start:
```

becomes:

```text
loop_start
```

---

# 108. `isLabelReferenced()`

This function checks whether a label is referenced elsewhere.

It:

1. Converts the target label to uppercase.
2. Scans every assembly line.
3. Ignores empty lines and comments.
4. Normalizes the line.
5. Skips the label's own definition.
6. Searches for the label name.
7. Checks token boundaries to reduce accidental substring matches.

This is used when removing consecutive labels.

---

# 109. Loading the Assembly File

`loadFile()`:

```cpp
ifstream inFile(inputFileName);
```

opens the input assembly file.

Every line is appended to:

```cpp
lines
```

If the file cannot be opened, an error is printed and the function returns.

---

# 110. `optimize()` — Main Optimization Loop

This is the core of the peephole optimizer.

It begins with:

```cpp
optimizationsCount = 0;
bool changed = true;
```

Then:

```cpp
while (changed)
```

keeps running optimization passes until a complete pass makes no change.

This is important because one optimization can expose another optimization.

---

# 111. `removed` Array

For every pass:

```cpp
vector<bool> removed(lines.size(), false);
```

is created.

Instead of immediately erasing lines from `lines`, the optimizer marks them as removed.

At the end of the pass, all unremoved lines are copied into `newLines`.

This avoids index problems while scanning the current vector.

---

# 112. Optimization Order

Inside the main loop, the optimizer checks patterns in this order:

1. Empty lines.
2. `foldPushOverwritePop`.
3. Matching `PUSH` / `POP` followed by dead overwrite.
4. Redundant `MOV`.
5. Redundant `PUSH` / `POP`.
6. Redundant arithmetic.
7. Jump to next label.
8. Redundant load after store.
9. Constant store simplification.
10. Consecutive labels.

This order is significant because an earlier transformation can change what later checks see.

---

# 113. Empty-Line Removal

If:

```cpp
isEmptyLine(lines[i])
```

is true, the line is marked removed.

The optimization counter increases.

The pass is marked as changed.

---

# 114. Four-Line Folding

The optimizer checks four consecutive lines:

```cpp
i, i+1, i+2, i+3
```

and calls:

```cpp
foldPushOverwritePop(...)
```

If successful:

- line `i` is replaced
- line `i+1` is removed
- line `i+3` is removed
- the optimization count increases

Line `i+2` remains because it is incorporated into the replacement logic.

---

# 115. Push/Pop Dead Overwrite Optimization

When a `PUSH reg` is found, the optimizer calls:

```cpp
findMatchingPop()
```

If it finds the matching pop and then sees an overwrite of that register, it removes both the push and pop.

The reasoning is that the saved value is never needed because it is immediately destroyed.

---

# 116. Removing Redundant `MOV`

If two consecutive instructions satisfy:

```cpp
isRedundantMOV(lines[i], lines[i + 1])
```

the second line is removed.

Example pattern:

```asm
MOV EAX, EBX
MOV EBX, EAX
```

The optimizer considers the second instruction redundant.

---

# 117. Removing `PUSH` / `POP`

If:

```asm
PUSH EAX
POP EAX
```

occurs consecutively, both are removed.

The optimizer marks both lines as removed.

---

# 118. Arithmetic Identity Removal

If a line matches `isRedundantArithmetic()`:

```asm
ADD EAX, 0
SUB EAX, 0
MUL EAX, 1
```

or the recognized `AND` identity, the line is removed.

---

# 119. Removing Jump to Next Label

For:

```asm
JMP target
target:
```

the `JMP` is removed.

This improves control flow without changing the intended local behavior.

---

# 120. Removing Reload After Store

For:

```asm
MOV [x], EAX
MOV EAX, [x]
```

the second instruction is removed when the exact matching structure is recognized.

---

# 121. Folding Constant Stores

For:

```asm
MOV EAX, 5
MOV [x], EAX
```

the optimizer attempts to produce:

```asm
MOV dword [x], 5
```

The first instruction is then removed.

---

# 122. Consecutive Label Optimization

If multiple labels occur consecutively, the optimizer examines each label.

An unreferenced label can be removed.

Referenced labels are retained.

This is necessary because simply deleting every duplicate/consecutive label could break jumps.

---

# 123. Rebuilding `lines`

At the end of each pass:

```cpp
for (...) {
    if (!removed[i]) {
        newLines.push_back(lines[i]);
    }
}
```

Then:

```cpp
lines = newLines;
```

So all marked lines are physically removed.

The process repeats if `changed == true`.

---

# 124. Why Repeat Until No Changes?

Suppose:

```text
Optimization A
      ↓
creates
      ↓
Optimization B
```

If the optimizer only made one pass, B might never run.

The:

```cpp
while (changed)
```

loop solves this by running another pass.

When an entire pass makes no change:

```cpp
changed == false
```

and optimization stops.

This is called reaching a local fixed point of the implemented transformations.

---

# 125. Writing the Optimized File

`writeOutput()` opens the output file and writes every remaining line:

```cpp
for (const string& line : lines) {
    outFile << line << endl;
}
```

Then closes the file.

---

# 126. Optimization Count

```cpp
int PeepholeOptimizer::getOptimizationsCount() const
```

returns:

```cpp
optimizationsCount
```

This lets the caller know how many optimization actions the optimizer performed.

The count is not necessarily the number of assembly lines removed, because some transformations replace or remove different numbers of lines.

# 127. Important Concepts for Viva

## Parse Tree

ANTLR converts source code according to `C4.g4` into a parse tree.

The `CodeGenarator` visitor walks that tree.

---

## Visitor Pattern

Methods such as:

```cpp
visitExpression()
visitTerm()
visitFactor()
```

correspond to grammar rules.

Each visitor generates assembly appropriate to that syntax node.

---

## Symbol Table

The symbol table stores information such as:

- variable names
- types
- global/local status
- array information
- stack offsets
- function information

The code generator uses `lookUp()` to retrieve symbols.

---

## Stack Frame

The function uses:

```asm
PUSH EBP
MOV EBP, ESP
```

to establish a frame.

Parameters are accessed using positive offsets such as:

```text
[EBP+8]
[EBP+12]
```

Local variables use negative offsets according to the symbol table.

---

## `EAX`

`EAX` is the main expression-result register.

Most visitors leave their computed value in `EAX`.

This creates a simple convention between visitor functions.

---

## `EDX`

`EDX` is important for division:

```asm
DIV EBX
```

For unsigned division, the dividend uses `EDX:EAX`.

The code clears `EDX` before division:

```asm
XOR EDX, EDX
```

The remainder is then in `EDX`.

---

## Labels

Labels implement control flow.

Examples:

```text
if_end_0
if_else_1
while_start_2
while_end_3
relop_true_4
relop_end_5
```

The `labelCount` makes them unique.

---

# 128. Important Source-Code Limitations to Know for Viva

These are observations directly supported by the uploaded implementation.

## 128.1 Floating-point code generation is not implemented

The grammar accepts `float` and floating constants, but the factor visitor generates:

```asm
MOV EAX, 0  ; float constant ignored
```

for `CONST_FLOAT`.

Therefore the implementation does not generate actual floating-point arithmetic.

---

## 128.2 `bodyLabel` in `for` is created but not emitted

The `for` visitor creates:

```cpp
string bodyLabel = newLabel("for_body");
```

but the shown code does not output:

```text
bodyLabel:
```

The body is visited directly.

This is a useful detail if asked to explain every local variable in the `for` implementation.

---

## 128.3 `getArrayAddr()` is defined but the shown array visitors calculate addresses directly

The helper exists, but `visitVariable()` and the array increment/decrement/assignment code perform their own address calculations.

---

## 128.4 `isEmptyOrComment()` exists but `optimize()` specifically calls `isEmptyLine()` for empty lines

The helper:

```cpp
isEmptyOrComment()
```

is present, but the main optimization loop uses:

```cpp
isEmptyLine()
```

for empty-line removal.

Comment handling mainly occurs through instruction normalization and label-reference scanning.

---

## 128.5 Some optimizer rules are intentionally pattern-based

The peephole optimizer does not perform a complete control-flow/data-flow analysis.

For example, it uses:

```cpp
maxLookahead = 6
```

when searching for a matching `POP`.

Therefore its decisions are based on the specific local patterns implemented in the source.

---

## 128.6 `isRedundantArithmetic()` uses exact textual constants

For example, the AND rule checks exact strings such as:

```text
-1
0FFFFFFFF
0FF
```

Therefore the optimizer is not a general symbolic algebra engine.

---

# 129. Example End-to-End Compilation

Consider:

```c
int main()
{
    int x;
    x = 5;
    println(x);
    return x;
}
```

Conceptually:

### Step 1 — Lexing

Tokens include:

```text
INT ID LPAREN RPAREN LCURL
INT ID
ID ASSIGNOP CONST_INT
PRINTLN LPAREN ID RPAREN
RETURN ID
RCURL
```

### Step 2 — Parsing

ANTLR builds a tree according to:

```text
program
  -> unit
      -> func_definition
          -> compound_statement
              -> statements
```

### Step 3 — Symbol table

`x` becomes a local variable with a stack offset.

### Step 4 — Function generation

The prologue is generated:

```asm
main:
    PUSH EBP
    MOV EBP, ESP
```

Local storage is allocated:

```asm
SUB ESP, ...
```

### Step 5 — Assignment

For:

```c
x = 5;
```

the value `5` is loaded into `EAX` and stored into `x`.

### Step 6 — `println`

The value is loaded into `EAX` and:

```asm
CALL OUTDEC
```

is generated.

### Step 7 — Return

`x` is loaded into `EAX`, then execution jumps to:

```text
main_exit:
```

### Step 8 — Exit

The main epilogue performs the Linux exit syscall.

### Step 9 — Peephole optimization

The generated assembly is scanned for local patterns such as redundant moves, push/pop pairs, arithmetic identities, and unnecessary jumps.

# 130. 10 Viva Questions with Answers

## Question 1
**What is the overall purpose of `C4.g4`, `CodeGenarator`, and `PeepholeOptimizer`?**

**Answer:**

`C4.g4` defines the lexical and syntactic structure of the C4 language. ANTLR uses it to create a lexer/parser and parse tree. `CodeGenarator` visits that parse tree and generates x86/FASM-style assembly. `PeepholeOptimizer` then reads the assembly and performs local instruction-level optimizations.

## Question 2
**Why does `CodeGenarator` use `EAX` so frequently?**

**Answer:**

The implementation uses `EAX` as the main register for expression results. Visitor functions evaluate their expressions and leave the result in `EAX`. This gives the different visitor functions a consistent interface. It is also used by function calls for return values and by `OUTDEC` for printing integers.

---

## Question 3
**How are local variables and parameters accessed?**

**Answer:**

The function first creates a stack frame:

```asm
PUSH EBP
MOV EBP, ESP
```

Parameters are assigned positive offsets starting from `EBP+8`, increasing by 4 bytes. Local variables are assigned stack offsets by the symbol table and are accessed relative to `EBP`, generally using negative offsets.

---

## Question 4
**How is `a[i]` translated into an address?**

**Answer:**

The index expression is evaluated into `EAX`. Since the implementation uses 4-byte elements, it multiplies the index by 4:

```asm
MOV EBX, 4
MUL EBX
```

The resulting byte offset is then combined with either the global array base or the local array's `EBP`-relative location.

## Question 5
**How does the code implement `if-else`?**

**Answer:**

It creates two labels: an else label and an end label. The condition is evaluated into `EAX`, followed by:

```asm
TEST EAX, EAX
JE elseLabel
```

The then-body is generated, followed by a jump to the end. The else label is then emitted and the else-body is generated. Finally the end label is emitted.

---

## Question 6
**How does the code generate `a < b`?**

**Answer:**

It evaluates `a`, pushes it, evaluates `b`, and pops `a` into `EBX`. Then it executes:

```asm
CMP EBX, EAX
JL trueLabel
```

If the relation is false, it sets `EAX` to 0. If true, it sets `EAX` to 1. Therefore relational expressions produce a Boolean-like integer result.

---

## Question 7
**Why is `XCHG` used for subtraction and division?**

**Answer:**

The left operand is pushed first and the right operand is evaluated into `EAX`. After popping, `EBX` contains the left operand and `EAX` contains the right operand. For subtraction, `XCHG EAX, EBX` makes `EAX` the left operand so `SUB EAX, EBX` computes left minus right. For division, it similarly makes the dividend the correct implicit `EAX` operand of `DIV`.

---

## Question 8
**What is peephole optimization? Give examples from this implementation.**

**Answer:**

Peephole optimization examines a small number of nearby assembly instructions and replaces or removes inefficient patterns without globally rebuilding the program. This implementation detects patterns such as:

```asm
PUSH EAX
POP EAX
```

redundant arithmetic like:

```asm
ADD EAX, 0
```

a jump directly to the next label:

```asm
JMP L1
L1:
```

and constant-store patterns such as:

```asm
MOV EAX, 5
MOV [x], EAX
```

which can be folded into a direct memory store.

---

## Question 9
**Why does `PeepholeOptimizer::optimize()` repeat until `changed` becomes false?**

**Answer:**

One optimization can expose another optimization. Therefore a single pass may not be enough. The optimizer repeatedly scans the assembly until a complete pass performs no transformation. At that point `changed` remains false and the optimizer has reached a fixed point for the implemented optimization rules.

---

## Question 10
**What important limitation exists regarding floating-point values?**

**Answer:**

The grammar recognizes `float` and `CONST_FLOAT`, but the shown code generator does not implement real floating-point code generation. In `visitFactor()`, a floating constant is translated to:

```asm
MOV EAX, 0  ; float constant ignored
```

So float syntax is accepted by the grammar, but the generated code does not actually represent or calculate the floating-point value.
